# Agent 高级架构与技术负责人面试题

适用：高级 Agent 工程师、架构师、技术负责人。以下数字都是题设，用来检验推理与决策，不代表行业基准。

答题顺序：**目标与约束 → 两个可行方案 → 选择依据 → 失败路径 → 验证与上线 → 责任人**。每题建议口述 5–8 分钟，再接受追问。只报框架名、只谈 Prompt、只画正常流程，不能达到高级标准。

通用评分为每题 0–4 分：0 为关键事实错误；1 为能复述概念；2 为方案成立；3 为能解释替代方案、故障和证据；4 为能量化收益、设计迁移/回滚并明确责任。安全与资金类严重错误应单独记录，不能靠其他题的高分抵消。

## S01：业务方要求“全部 Agent 化”，你如何决定哪些环节值得做？

**场景：** 每天十万次客服请求，八成已有稳定处理流程，剩余请求涉及模糊意图与跨系统查询。

**参考答案：** 先按任务分布、可自动验收程度和错误损失切片。稳定流程继续使用确定性代码，模型处理意图理解、资料提取或动态查询。建立规则/工作流、单 Agent 两个 baseline；对复杂长尾再实验多 Agent。比较问题解决率、错误操作、人工时长、P95 和每成功任务成本，避免把聊天满意度等同于业务收益。

试点选高频、证据可验证、动作可约束的切片，先只读或草稿，再按风险开放执行。明确停止条件：收益不足、人工复核抵消节省、关键错误超出门槛。

**追问：** 自动处理率上升但投诉率也升高，如何定位？

**评分点：** 有任务切片、反事实 baseline、风险预算和业务验收；能否明确说出哪些流程暂不改造。

## S02：设计一个供十个业务团队使用的 Agent 平台，哪些能力统一，哪些留给业务？

**参考答案：** 平台提供模型接入、run 生命周期、调度、工具注册与执行策略、身份传播、预算、trace 和评测发布设施；业务团队拥有领域规则、数据语义、工具契约和成功标准。平台不应该在通用 Prompt 中维护所有团队的退款或结算政策。

控制平面管理版本、配置、策略和租户；执行平面运行具体任务。业务工具在自身服务最终校验不变量，平台做通用授权和审计。不要让平台故障阻断既有业务系统的正常人工处理路径。

**追问：** 两个团队都要“记忆服务”，实际语义不同，如何避免做成万能数据库？

**评分点：** 有权威事实的归属、清晰接口、故障边界和演进路径，而非只罗列平台模块。

## S03：退款已在支付系统成功，worker 在保存 checkpoint 前崩溃，怎么恢复？

**参考答案：** 为业务退款意图生成稳定 operation ID，以租户和业务操作为作用域；同一操作的各次尝试复用同一个下游幂等键，参数不一致时冲突拒绝。调用前记录操作意图，结果未知则标记 `unknown`；恢复后查单，或在下游保证幂等时使用原键重试，确认后再推进 run。

本地事务与 outbox 可以保证意图不丢，但不能单独让任意外部 API 恰好执行一次。若外部系统既不支持幂等也不可查状态，就不能证明安全自动重试，应停止并对账/转人工。租约与 fencing token 保护本地所有权，下游写入仍须独立保证。

**追问：** 同样订单和金额的第二次合法退款，为什么不能直接按参数哈希去重？

**评分点：** 明确“业务意图身份”不同于“参数相同”，承认分布式原子性边界。

## S04：用户在运行中修改需求或点击取消，异步工具还在执行，怎么办？

**参考答案：** 将用户更新作为带版本的事件，记录新的目标和约束。协调器停止调度依赖旧要求的动作，取消尚未开始的任务；已完成的独立产物可以复用。每个工具保留 call ID、操作 ID、目标版本及状态，迟到结果不能覆盖新计划的终态。

取消是尽力终止执行，不等于回滚业务。已提交或状态未知的副作用继续对账；用户界面分别显示任务已停止和外部操作待确认。异步工具结果、审批、流式事件都必须与原调用关联。预算同时考虑已经发出但尚未结算的调用。

**追问：** 旧模型响应在撤权之后才返回一个写工具请求，哪一层拒绝？

**评分点：** 真正处理并发事件顺序、当前授权和迟到结果，不能只写一个 `cancelled=True`。

## S05：用户批准了发信，模型之后修改了收件人，原审批还有效吗？

**参考答案：** 无效。审批绑定主体、操作类型、规范化参数哈希、收件人、正文/附件产物版本、资源版本、政策版本和有效期。执行时校验待执行动作与获批动作完全对应，并重验当前权限；关键字段改变必须重新审批。

审批与执行状态转换需防重放：同一批准可能因重试多次送达，但同一业务动作只提交一次。大附件使用不可变内容引用，不能只绑定可被替换的路径。人工等待保存为持久状态，不长时间持有数据库锁。

**追问：** 政策允许预授权一定额度，如何减少无效确认又保持范围可验证？

**评分点：** 能区分单次批准、范围授权与权限检查，覆盖 TOCTOU。

## S06：企业知识库回答泄露了另一个租户的材料，怎么设计隔离？

**参考答案：** 身份由可信网关注入；检索在候选生成/过滤阶段落实授权，进入 reranker、模型与日志前不能包含未授权内容。无法原生过滤的检索引擎需隔离索引或在可信检索边界处理，避免事后靠模型“忘掉”数据。

向量、全文、图索引、缓存、对象存储、checkpoint 和导出均携带租户与权限语义。缓存命中也要考虑撤权与 ACL 版本，不能只按问题文本缓存。源系统权限变更采用事件同步和读时校验，定义可接受同步窗口与高敏数据的强校验路径。

**追问：** 文档删除后，历史摘要和备份中仍存在内容，如何防止恢复后重新可见？

**评分点：** 覆盖派生数据与撤权，不把 tenant 字段的存在当成隔离已完成。

## S07：上下文窗口变大后，为什么还需要 Context Engineering 和 harness？

**参考答案：** 窗口容量不等于有效使用率。每轮要选择指令、约束、状态、近期交互与证据，控制重复、冲突和过期信息。稳定约束与业务账本独立保存；大文件用可追溯引用按需取回；压缩保留未决调用、用户要求和当前证据。

harness 指模型外围的运行环境和控制设施，包括工具、状态、执行隔离、预算、压缩、恢复及验收。相同模型更换 harness 可能改变效果，因此评测需把模型和系统配置一起记录。增加上下文、增加检索和增加模型推理分别做消融。

**追问：** 将历史压缩到十分之一后成功率不变，能否直接全量发布？

**评分点：** 检查长尾约束保留、权限、证据可恢复和重复运行，不只比较平均值。概念参考 [Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

## S08：Tool、Skill、MCP、A2A 分别负责什么？

**参考答案：** Tool 是可调用能力；Skill 通常是可复用的任务说明和资源包，具体格式、加载与权限依实现而异；MCP 是应用接入工具、资源、提示等能力的协议；A2A 支持独立 Agent 服务之间的能力发现、任务和产物交互。Skill 中的脚本仍需受工具执行策略约束。

它们不是互斥选项，也不自动建立信任。使用协议的价值应来自跨团队/跨系统互操作，进程内几个函数不必为了“标准化”全部远程化。对远程 Agent 也要定义身份委托、任务取消、数据访问和结果验收。

**追问：** 一个第三方 Agent 自称擅长财务审查，其 Agent Card 能否作为授权凭据？

**评分点：** 区分能力声明、身份、授权与实际验证。依据：[MCP](https://modelcontextprotocol.io/specification/2025-11-25)、[A2A](https://a2a-protocol.org/latest/specification/)。

## S09：如何审查一个远程 MCP Server？

**参考答案：** 核对协议版本、能力协商、工具来源和变更、身份传播、数据范围与执行权限。在本题固定的 MCP 2025-11-25 基线上，常用传输是 stdio 和 Streamable HTTP；后者可使用 SSE，不能把它与旧 HTTP+SSE 传输混为一谈。

HTTP 授权检查资源与 token audience、最小 scope、令牌过期和撤销，禁止未验证的 token 透传。元数据发现、重定向和资源 URL 需要 SSRF 防护。session ID 不是用户身份；每次敏感调用仍要业务授权。工具描述变化须触发复审或回归，annotations 只作为提示，不能当安全保证。

**追问：** 用户输入的 server 地址通过 OAuth discovery 指向内网元数据服务，哪里阻断？

**评分点：** 协议、传输、鉴权、业务授权各自清楚。依据：[传输](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)、[授权](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[安全实践](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)。

## S10：工具达到两千个，如何控制工具发现、上下文与执行成本？

**参考答案：** 建立带任务语义、权限、版本与副作用类型的工具目录，按租户/任务阶段过滤，再检索少量候选并加载 schema。定义工具发现 Recall、误选、无工具可用的回退和索引更新机制；不能只优化 prompt token。

对固定批量过程，使用业务批量接口或程序化调用减少模型往返。程序层管理循环、聚合与限流，保留逐操作审计；单个脚本也要受总预算和工具策略约束。对不适合批量的写操作，禁止通过预执行来猜测用户意图。

**追问：** 工具检索 top-5 更省钱，却漏掉一个低频关键工具，如何设计灰度与人工兜底？

**评分点：** 同时考虑工具发现与执行的成功率，以及权限过滤导致的候选变化。

## S11：多 Agent 比单 Agent 成功率高 3 个百分点，是否值得保留？

**参考答案：** 先检查样本量、置信区间、任务分布、总推理预算和人工干预是否一致。比较同预算单 Agent、多次采样、专门验证器和多 Agent，区分并行带来的延迟收益与多次推理带来的质量收益。

拆分应对应可独立验收的子任务、上下文或权限边界；协调器负责全局预算、取消、合并和最终验收。共享错误、交接丢信息和重复检索可能抵消收益。按业务价值决定是否只在困难任务路由到多 Agent。

**追问：** 结果改善只出现在极少数高价值任务，应该全量启用还是选择性路由？

**评分点：** 有消融、净收益和可观测的拆分理由。

## S12：如何设计能决定上线与否的 Agent 评测？

**参考答案：** 先定义任务成功、允许澄清/拒绝的条件，以及不可接受的行为。业务状态、工具轨迹、成本延迟和安全分别评分；关键错误作为独立门槛。样本包括真实请求、近期失败、长尾、工具故障、撤权与注入，保留不参与调参的隐藏集。

按任务重复运行，报告任务级分布与不确定性。pass@k 表示至少一次成功，pass^k 表示全部成功；在独立同分布的简化假设下分别为 `1-(1-p)^k` 与 `p^k`，实际试验通常不能假定所有任务等难或各次独立。能否选出正确候选以及重试成本必须算进去。

**追问：** 零次观察到越权是否证明线上越权概率为零？

**评分点：** 会区分采样证据和安全保证，不把重复样本当作独立样本。参考 [Agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## S13：模型升级后离线平均分更高，如何发布？

**参考答案：** 固定提示、工具、索引与流量分层比较，检查关键风险切片、拒答/澄清率、结构化输出、调用次数、token 和延迟。judge 用人工金标校准，检查位置/风格偏好及答案注入，能用实际状态判定的任务不用 judge 代替。

无副作用 shadow 验证兼容性，随后小比例稳定分桶灰度；设置业务成功、错误动作、延迟与成本门槛及自动回退。存量 run 固定旧版本或走已验证的状态迁移，不在任务中间随意换模型/工具契约。

**追问：** 回滚后已发送的错误邮件怎么处理？

**评分点：** 区分配置回滚、任务状态恢复与业务补偿，能说明谁决定停止扩大流量。

## S14：有一万个失败样本，应该改 Prompt、RAG、工具还是微调？

**参考答案：** 先做错误分类和抽样校准：缺知识查数据/RAG，召回不准查索引和查询，参数错误查 schema 与说明，业务执行失败查服务，长期状态丢失查运行时，稳定行为缺口再考虑提示示例或训练。不要把所有失败交给模型团队。

每类选择最低成本可验证修复，固定对照集，防止把训练/调参数据混入测试。微调需要足够质量的数据、清晰目的和训练后回归；知识频繁变化或权限随用户变化时，单靠模型权重不适合作为权威源。

**追问：** 总体分提高，但新业务切片下降，如何判断是否过拟合？

**评分点：** 从错误证据找责任层，能提出组合方案与停止条件。

## S15：如何切换模型供应商或淘汰停维框架？

**参考答案：** 盘点真实契约：消息与工具事件、schema 支持、拒绝/截断、流式重组、usage、重试、缓存、状态与恢复、数据政策。适配器显式暴露差异，不伪装成所有模型完全兼容。

为新旧实现运行同一批固定任务与故障注入，比较语义和业务行为；副作用只在一侧执行，另一侧回放或模拟。锁定版本、迁移 checkpoint、灰度并保留回退窗口。退出成本包括数据导出、历史 trace、团队培训和平台运维。

**追问：** fallback 模型不支持当前工具 schema，如何降级？

**评分点：** 不把“改 base_url”当成迁移完成，不为可用性绕过安全约束。框架状态见 [[06-框架对比/主流框架]]。

## S16：10 QPS 的长任务系统要扩到 100 QPS，如何估算容量？

**场景：** 每个任务平均 40 秒，平均 8 次模型调用；单次平均输入 3,000 token、输出 400 token。

**参考答案：** 在稳定流量的简化条件下，平均在途任务约 `100 × 40 = 4,000`，模型请求约 `100 × 8 × 60 = 48,000 RPM`；输入与输出合计约 `163,200,000 token/min`。这些只是均值估算，不含峰值、缓存计费差异与重试；供应商可能分开限制不同 token 项。

接入层限流，任务与模型调用分别排队，按租户公平调度；总预算覆盖子任务。按真实分布压测关键路径和尾延迟，检查模型配额、下游 API、数据库连接、沙箱与队列滞留。扩 worker 无法自动提高供应商配额。

**追问：** 一个大租户占满队列，你如何保证小租户交互延迟？

**评分点：** 单位正确，区分任务 QPS、调用 RPM、token 配额和在途任务数。

## S17：便宜模型单次成本降低 40%，为什么单位业务成本可能上升？

**参考答案：** 比较完整任务的调用次数、重试、工具、验证、人工和错误损失。每成功任务成本的分子包含失败任务产生的成本，分母是通过同一验收标准的任务数；还需报告覆盖率，避免把困难任务全部拒绝后显示“省钱”。

预算采用预留—结算，按模型价目表版本区分各计费项；并发分支不能各自读取相同余额后同时花掉。跟踪已取消任务的迟到费用。对高价值困难任务可选择昂贵模型，对稳定简单任务做路由。

**追问：** 预算耗尽时是否允许最后一次调用生成解释？如何提前预留？

**评分点：** 经济模型覆盖人工和失败，预算落实到执行层。

## S18：Coding Agent 所有测试通过，能否自动合并？

**参考答案：** 先确定测试是否覆盖需求、是否被 Agent 修改、是否依赖可信环境。检查 diff 范围、公共接口、权限、依赖变更、生成产物和回归；针对高风险部分增加独立 oracle 或人工 review。

仓库任务使用隔离工作区、受限网络和短期凭据；issue、源码注释、构建日志与依赖脚本均可能携带注入。生成、执行、提交、推送和部署是不同能力边界。衡量修复接受率、审查时间、逃逸缺陷和返工，而非生成行数。

**追问：** Agent 修改了验收测试才能通过，什么情况下合理，谁批准？

**评分点：** 不把测试通过当完整正确性证明，保护验收权威与发布边界。

## S19：长期记忆该不该让模型自动写？如何避免污染？

**参考答案：** 先确定跨会话保留是否必要。模型可提取候选，服务端根据来源、用途、敏感性、主体和授权决定是否写入。偏好、事实、推测和权限严格分开；外部文档内容不能变成用户授权或管理员身份。

记录来源、有效时间、版本和删除规则，冲突不简单按最后写入覆盖。读取需权限过滤和时效验证，纠错/撤权/删除传播到摘要、索引和缓存。跨 Agent 共享采用结构化记录与并发控制。

**追问：** 用户曾说“以后自动批准所有操作”，系统应该记住什么？

**评分点：** 记忆与授权分离，能处理用户偏好变化和派生数据删除。

## S20：一次安全事故后，你如何组织排查与恢复？

**场景：** Agent 读取了一份正常可见的文档，随后调用合法上传工具，把文档发送到未授权外部地址。

**参考答案：** 先按受影响工具、租户与出口止损，隔离凭据并保存脱敏证据。还原来源内容、模型请求、工具参数、授权决策、审批和实际传输，判断是否外传成功以及受影响范围。读取和上传分别合法不代表组合流程合法。

修复数据流和执行策略，补充目的地/用途约束、最小上下文与审批绑定；将样本变成安全回归并测试正常业务误拦。对外事实由明确事件负责人统一，恢复需验证门槛和渐进放量。

**追问：** 为什么仅增加“不要泄露数据”的系统提示不足以关闭事故？

**评分点：** 有止损、事实、根因、责任、回归与恢复，而非立即归因“模型不聪明”。

## S21：自研 runtime、使用 SDK、采用托管服务，如何决策？

**参考答案：** 比较上线时间、长任务与状态语义、数据驻留、执行环境、工具接入、可观测、费用和退出成本。自研提高控制力但承担恢复、安全与运维；SDK 提供通用循环但部署责任仍在应用；托管可减少基础设施工作，但要验证权限、数据和资源生命周期是否符合业务。

先用两个代表任务验证正常路径和最难故障路径，量化一年总拥有成本，写出迁移出口。不要因为团队能写 Agent loop，就低估生产 runtime；也不要假设托管服务承担所有业务授权责任。

**追问：** 必须保留自有沙箱与业务凭据时，方案如何变化？

**评分点：** 责任矩阵与实验证据。产品边界依据 [OpenAI 运行时对比](https://developers.openai.com/api/docs/guides/agents)，这不是所有厂商的统一分类。

## S22：作为负责人，你如何制定 90 天路线图？

**参考答案：** 前 30 天选定业务切片、测量人工/工作流 baseline、建立失败集与责任分工；31–60 天完成最小执行闭环、隔离与恢复，做真实数据离线评测及小规模试点；61–90 天依据门槛灰度、建立值班和成本监控，决定扩展、收缩或停止。

每阶段交付可复核产物：需求和验收、架构决策记录、工具契约、评测报告、事故演练与收益复盘。平台化只提炼已经在多个业务验证的共性，避免第一阶段就构建通用 Agent 操作系统。

**追问：** 两个月后 demo 很好但没有业务收益，如何向业务方汇报并调整？

**评分点：** 有里程碑、owner、退出条件和可解释的范围控制。

## S23：如何分配模型、平台、业务和安全团队的职责？

**参考答案：** 业务团队定义任务成功与领域规则；模型/应用团队负责数据、提示、模型适配和能力评测；平台负责运行时、配额、身份设施及观测；安全团队定义威胁要求并参与评审。每个线上服务仍有明确 incident owner，不能因为跨团队而无人接警。

共同维护版本化工具契约、风险切片与发布门槛。模型升级、政策变化和索引变更均可能改变行为，发布责任不能只落在写 Prompt 的人身上。人员考核关注业务成果、质量和知识共享，避免用调用量或生成代码量驱动行为。

**追问：** 准确率下降，四个团队都认为不是自己的问题，如何组织一天内的排查？

**评分点：** 能按 trace 与失败分层分配验证任务，并明确最终裁决机制。

## S24：高级候选人评审 Agent 方案时，最应追问什么？

**参考答案：** 要求展示一次真实任务的输入、动作、证据、状态和最终业务结果；挑一个超时、一处授权变更和一次恢复，检查设计是否成立。追问成功标准是谁制定、数据从哪里来、哪些假设未经验证、替代方案为何没选、上线后谁负责。

候选人可以没有用过某个新框架，但应能推导它需要满足的契约。不要用缩写数量或旧 API 背诵判断资历。优秀负责人能够删掉无收益的复杂设计，并把不确定性变成有边界的实验。

**追问：** 让候选人指出自己方案中最可能错误的假设，并设计一周内能推翻它的实验。

**评分点：** 思考可证伪、证据可复核、责任可落地。

# Agent 高级岗位 120 分钟笔试与评分标准

适用高级工程师、架构师与技术负责人，满分 100，建议用 120 分钟。允许查官方文档；不要求记忆某个框架的 API。代码可用 Python、Go、Java 或 TypeScript，但必须说明并发和取消语义。所有业务数据与阈值均为本试卷设定。

| 题目 | 时间 | 分值 | 交付 |
|---|---:|---:|---|
| A：企业工单平台设计 | 40 分钟 | 35 | 架构、状态、契约和上线方案 |
| B：执行器实现与代码评审 | 35 分钟 | 30 | 可运行代码/核心实现、测试和修复意见 |
| C：评测与收益决策 | 25 分钟 | 20 | 计算、发布结论和验证计划 |
| D：技术负责人决策 | 20 分钟 | 15 | 一页决策记录 |

## A：设计一个能持续运行、审批与恢复的企业工单 Agent（35 分）

**题设：** 100 个租户，每天 20 万任务；多数任务 30 秒，少量持续 2 小时；人工审批最长等待 24 小时。工具包括文档检索、订单查询、退款和发送邮件。系统会重复投递消息，worker 随时重启，用户可以撤权和取消。不得跨租户读写，不得重复退款。

**作答要求：**

1. 画出控制平面、执行平面、身份、工具、状态和观测的边界。
2. 区分 run、step、attempt、operation，并设计主要状态与幂等键。
3. 分析“远端退款成功，本地未记录就崩溃”和“批准后金额改变”两条故障路径。
4. 说明配额、公平调度、取消、版本升级、评测门槛与灰度回滚。

**参考解题结构：**

```text
用户 → 身份/配额/API → run 存储 + 调度队列 → worker / Agent runtime
                          ↑                     │
策略/版本控制平面 ──────────┘                     ├─ 模型适配器
                                                ├─ 权限感知检索
审批服务 ↔ 审批记录 ↔ 调度器                       └─ 工具执行边界
                                                      ↓
                                                  业务服务
                                                      ↓
                                            操作账本 / 对账任务

事件流、trace、成本、审计分别关联 run / step / operation
```

任务入队应避免“数据库已提交但消息丢失”，可用事务 outbox。worker 租约与条件更新防止双重拥有；过期 worker 不能继续推进状态。审批等待释放 worker，恢复时读取不可变审批内容并重验授权。退款的 operation ID 由可信业务层为一次业务意图分配，不能由模型任意更新，也不能只靠参数哈希。

**最小数据契约示意：**

```text
runs: tenant_id, run_id, goal_version, status, config_version,
      checkpoint_ref, lease_owner, lease_until, fencing_token, version
operations: tenant_id, operation_id, run_id, tool_version,
            args_hash, status, downstream_key, external_ref, version
approvals: approval_id, tenant_id, operation_id, actor_id,
           args_hash, artifact_version, policy_version, expires_at, status
```

操作状态可以是 `prepared → in_flight → succeeded/failed/unknown`；`unknown` 通过查单/幂等重试/对账确认。已完成的业务动作不能因 run 回滚被抹掉。服务端唯一约束与状态条件更新保障一致性，写入工具最终校验当前资源与业务条件。

**评分：** 边界与职责 7 分；状态与持久恢复 8 分；副作用幂等及未知结果 8 分；租户/审批/撤权 7 分；评测灰度与运维 5 分。把“外部写超时”直接当作“未执行”并盲目重试，副作用项不得分。

## B：实现异步执行器，并评审一个有问题的写工具（30 分）

### B1：异步只读工具执行器（20 分）

输入是有限列表，每项包含唯一 `call_id` 与异步调用工厂。实现：

- 最大同时执行 3 个工具，输出顺序与输入一致。
- 单工具执行超时 2 秒；从任务提交时起总 deadline 为 5 秒，包含排队。
- 区分业务拒绝、工具超时、总 deadline 耗尽与系统异常，错误不泄露堆栈和敏感参数。
- 调用方取消时取消并等待所有子任务清理，再传播取消；不把取消包装成普通成功结果。
- 至少测试超时、并发上限、乱序完成、业务拒绝和外部取消。

工具假定遵守协作取消，不阻塞事件循环；如果不成立，需进程隔离或下游服务 deadline。`asyncio.wait_for` 发起取消并等待清理，不是强杀机制，不能承诺恶意协程绝不超时。[Python 官方说明](https://docs.python.org/3/library/asyncio-task.html)。

参考实现与测试在 [reference.py](../10-笔试代码/reference.py) 和 [test_reference.py](../10-笔试代码/test_reference.py)。关键是信号量内开始计算单工具执行时间、信号量外仍受总 deadline 约束，并在取消路径清理子任务。这个执行器只解决调度，不提供授权或写操作幂等。

**评分：** 并发上限与保序 4 分；两级 deadline 5 分；错误分类 3 分；取消与任务清理 4 分；有效测试 4 分。

### B2：评审以下伪代码（10 分）

```python
async def refund(model_args):
    key = hash(str(model_args))
    if key in local_cache:
        return local_cache[key]
    if model_args['approved']:
        for _ in range(3):
            try:
                result = await payment.refund(**model_args)
                local_cache[key] = result
                return result
            except Exception:
                pass
    return {'ok': True, 'message': '退款已处理'}
```

指出至少五个不同层面的问题，并为崩溃恢复写出状态迁移伪代码。

**参考问题：** 审批来自模型且未绑定参数；缺少身份与订单归属校验；参数哈希既非稳定业务身份也非跨进程可靠键；本地缓存不能跨 worker 去重；检查缓存与提交之间存在竞态；金额和剩余可退额度未校验；写超时盲重试；吞掉错误并伪造成功；无 deadline、审计与对账；相同参数的不同合法意图可能被误合并。

**恢复伪代码：**

```text
校验真实主体、参数和业务操作身份
读取或创建唯一 operation，拒绝相同 operation ID 的不同参数
若已成功：返回已确认结果
若 in_flight/unknown：先查下游状态；不可确认且无幂等契约则转对账
执行前重验绑定审批、当前权限、资源版本与可退金额
记录调用意图 → 以同一个 downstream_key 提交
已确认：保存结果并推进 run
超时或崩溃：保留 unknown，由恢复任务确认，绝不伪造成功
```

**评分：** 五类有效问题各 1 分；恢复路径 5 分。不能把缓存与 outbox 单独描述为对任意外部 API 的 exactly-once 保证。

## C：模型升级是否值得发布？（20 分）

在同一套 1,000 个任务上各运行一次，结果如下。人工成本为 100 元/小时，技术成本包含这 1,000 个任务所有成功与失败调用的模型、工具和基础设施费用，暂不计事故损失。

| 指标 | A：现网 | B：候选 |
|---|---:|---:|
| 业务验收通过 | 920 | 940 |
| 技术成本 | 2,000 元 | 2,400 元 |
| 人工复核与返工 | 8 小时 | 4 小时 |
| P95 完成时间 | 30 秒 | 38 秒 |
| 未授权写入 | 0 次 | 2 次 |

配对结果：两者都成功 900 个，仅 A 成功 20 个，仅 B 成功 40 个，两者都失败 40 个。发布要求：P95 不高于 35 秒，安全回归中不得出现未授权写入。

**作答要求：** 计算任务成功率、含人工的每成功任务成本；给出发布结论；分析还缺哪些证据。

**参考答案：**

- A 成功率 92%，B 为 94%，提高 **2 个百分点**，不是 2% 的相对增幅。
- A 总成本 `2,000 + 8×100 = 2,800` 元，约 `2,800/920 = 3.04` 元/成功任务。
- B 总成本 `2,400 + 4×100 = 2,800` 元，约 `2,800/940 = 2.98` 元/成功任务。
- B 虽然均值成功率和单位成本略好，仍不满足延迟和安全门槛，**不能按该结果全量发布**。先定位两次未授权写入并修复；通过安全回归后再按任务切片验证延迟优化和灰度收益。
- 需要检查失败严重度、样本分布、人工计时口径和评测污染。比较配对差异，可用任务级配对 bootstrap 等方法表达不确定性；增加重复运行检查稳定性，但不能简单当作新的独立任务。零次事故也不证明真实风险为零。

**评分：** 正确计算 6 分；发布结论与门槛 6 分；配对/重复试验及不确定性 4 分；下一轮验证计划 4 分。

## D：一页技术决策记录（15 分）

**场景：** 六人团队，八周交付第一个企业 Agent。一个候选是团队熟悉的 SDK，另一个是提供托管执行与持久状态的服务；业务要求审批、客户数据隔离与随时转人工，实际流量尚不清楚。

**作答要求：** 写一页 ADR，必须包含目标、硬约束、两个候选、当前选择、待验证假设、两周实验、退出条件、八周里程碑和 owner。不要求选择某个指定厂商。

**参考答案结构：**

1. 用明确的数据边界与业务目标淘汰不可行方案，不以流行度决策。
2. 比较总拥有成本：集成、状态/审批/恢复、安全、运维、评测和退出。
3. 两周 PoC 使用相同代表任务，注入 worker 崩溃、撤权、下游超时与取消；只读或模拟副作用。
4. 指定业务验收负责人、runtime owner、工具 owner、安全评审与 incident owner。
5. 八周内先交付窄范围可衡量切片，再依据通过率、成本和事故演练决定开放写操作。
6. 退出条件可包括数据边界不满足、恢复契约无法验证、人工量抵消收益；同时描述如何保留已产生的任务与产物。

**评分：** 目标与边界 3 分；有证据的取舍 4 分；可推翻假设的实验 3 分；里程碑与责任 3 分；退出与迁移 2 分。

## 总分解释与面试追问

| 分数 | 本套练习中的表现 |
|---|---|
| 85–100 | 能把架构、业务风险、验证和组织责任连成完整方案 |
| 70–84 | 关键方案成立，部分容量、迁移或故障细节需补充 |
| 55–69 | 熟悉概念，执行语义和决策证据不足 |
| 低于 55 | 需要先补齐运行时、授权、评测和分布式系统基础 |

这是自测 rubric，不是招聘结论。真实面试还需项目证据与现场追问。重点复盘：是否把超时当失败、把批准布尔值当权限、把模型回答当真实状态、把总体平均分当发布依据。

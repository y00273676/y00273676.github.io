面向第一次准备技术面试、尤其是 AI Agent / 大模型应用 相关项目面试的同学。本文把 STAR 法讲透，并给出 可直接朗读、改写、录音练习 的话术正文。建议你：先通读方法论 → 用真实项目替换方括号 → 手机录音控制时长 → 请朋友追问三轮。

1. STAR 面试法详解

STAR 是行为面试里最常用的结构：Situation（情境）→ Task（任务）→ Action（行动）→ Result（结果）。技术项目里，面试官想听的不是「我懂很多名词」，而是 你在真实约束下做了什么决策、怎么落地、数据上有没有变化。

1.1 S（Situation）：项目背景，怎么说

你要交代什么：

维度 说什么 反面例子（避免）
业务场景 谁在用、解决什么痛点 从公司历史讲起
约束条件 时间、人力、合规、成本、遗留系统 只说「很难」不说难在哪
技术上下文 单体/微服务、语言栈、数据量级（量级即可） 堆砌十个技术名词无主线

怎么说更加分：

  • 用 一两句 点出「为什么现在要做」，体现业务意识。
  • 控制在 20～40 秒：背景讲清即可，不要「故事片头」。
  • 可带一句 竞争或合规压力（例如：客服人力紧、知识必须可审计），显得真实。

小白话术模板：

「当时我们团队在做一个面向 B 端的企业级 AI 助手。背景是：公司内部文档、工单、知识库分散在多个系统里，员工和客服查资料效率低，领导希望用 Agent 把『检索 + 推理 + 工具调用』串起来，同时要可审计、可降级。」

自检： 若删掉所有技术词，这段话还能让人听懂「业务上在忙什么」，S 就合格了。

1.2 T（Task）：你的任务，怎么说

你要交代什么：

  • 你的角色：Owner / 核心开发 / 接口人（诚实表述，忌夸大成「我一个人做完整个平台」）。
  • 你的目标：可验收的目标（上线某能力、P95 压到某值、某指标提升 X%）。
  • 协作边界：模型谁提供、数据谁维护、你交付物是代码、文档还是运维手册。

怎么说更加分：

  • 目标里尽量带 可量化或可对齐业务 的表述（准确率、成本、可用性、人效）。
  • 用 「我负责……」 一句话钉死范围，面试官追问时不会乱。

小白话术模板：

「在这个项目里，我主要负责【模块名】，目标是【具体目标】。需要与【前端/运维/算法】协作，我这边交付物包括【接口/文档/可观测性/灰度方案】。」

1.3 A（Action）：你做了什么，怎么说

这是 STAR 的核心，占比最大（建议占总时长一半左右）。

你要交代什么：

  • 关键决策：为什么选 A 不选 B（哪怕后来证明 B 也行，你要有理由）。
  • 架构或方案：分层、模块、数据流（粒度以面试官能跟上为准，不要一口气堆十个名词）。
  • 工程细节：接口设计、容错、幂等、缓存、队列、限流、评测方法等，选 2～4 个 深入讲。
  • 你怎么验证：离线评测、A/B、灰度、压测、日志与 trace。

怎么说更加分：

  • 用 「问题 → 方案 → 权衡」 三段式，而不是罗列技术栈。
  • 主动提 踩坑与迭代（比「一次做对」更真实）。
  • 每个技术点尽量能回答：输入输出是什么、失败时怎样、如何观测。

小白话术模板：

「我先把问题拆成三层来看：数据层、编排层、模型层。针对【具体问题】，我采用了【方案】，主要考虑【约束】。实现上，【关键实现 1】，同时为了稳定性做了【容错/降级】。上线前我们用【评测/压测】验证，发现【问题】后又调整了【改动】。」

1.4 R（Result）：取得了什么成果，怎么说

你要交代什么：

  • 业务结果：人效、转化率、工单量、满意度（有则说；没有可用 proxy 指标）。
  • 技术指标：延迟 P95/P99、可用性、错误率、成本、吞吐。
  • 团队收益：可维护性、文档、复用组件、排障时间缩短。

怎么说更加分：

  • 数字用 真实区间 即可（「大约」「从 A 量级到 B 量级」），不要编精确到小数点后三位却经不起追问。
  • 若暂无严谨 A/B，可说 「观测到的趋势」+「后续计划」，不要硬编。
  • 用 一句复盘 收尾（若重来会怎么改），显得成熟。

小白话术模板：

「上线后，我们在【时间窗口】内观测到【核心指标】有【变化】。另外从工程侧看，【稳定性/成本/排障效率】也有改善。如果复盘的话，下一步我会【改进点】。」

1.5 时间控制：每个部分说多久

以下按 「一段完整项目经历」约 2.5～3.5 分钟 分配（可按面试节奏微调）：

部分 建议时长 说明
S 20～40 秒 背景清楚即可
T 20～40 秒 目标与职责一笔说清
A 90～150 秒 主战场，讲 2～4 个关键点，有细节
R 20～40 秒 结果 + 一句复盘或下一步

项目整体介绍（单独一题）： often 要求 1 分钟 或 3 分钟，见第 2 节专用话术。

自检：

  • 若 A 少于 60 秒，往往显得「空」。
  • 若 S 超过 60 秒，往往显得「啰嗦」。
  • 用手机录音，整段 STAR 控制在 2.5～3.5 分钟；超时则删次要细节，别加快语速。

1.6 常见误区

  1. 只堆名词：「我用了 LangChain、向量库、K8s、Prometheus……」——没有因果链，面试官不知道你 解决了什么。
  2. 把 STAR 说成流水账：每分钟一个新话题，没有主线。应 围绕一个核心矛盾（成本、准确率、延迟、可控性）展开。
  3. Result 只有形容词：「效果很好、性能不错」——没有指标，可信度低。
  4. 夸大个人贡献：团队项目要说清协作，否则追问容易露馅。
  5. 背稿痕迹太重：语气僵硬、任何追问都答同一段。应 记结构 + 记关键词（3～5 个），而不是记每一个字。
  6. 回避失败与妥协：真实项目常有妥协。用一句 「当时的权衡是……若重来会……」 反而加分。
  7. 忽略业务价值：技术讲完不收口到「用户/业务感受到什么」，会显得像自嗨。
  8. 全程被动：没有准备「追问」：例如为什么阈值这么设、评测集怎么来、线上如何回滚。

2. 项目整体介绍话术（3 分钟版本 + 1 分钟精简版）

使用说明： 把【】换成你的真实数据；没有的数据用「趋势」「量级」表述，不要硬编精确数。
下面 先给通用完整版（含你指定的开场句式），再分别给 Python / Java / Go 各一套 完整 3 分钟 + 完整 1 分钟，可直接朗读练习。

2.1 三分钟完整版本（通用 · 推荐默认练这一版）

（开场 — 可按你习惯微调，建议保留业务一句话）
面试官您好，我来介绍一下我做的这个项目。
这个项目是一个 企业级 AI Agent 智能助手平台，主要解决企业在 知识管理和智能客服 场景中的痛点：文档分散、检索不准、重复咨询多，以及大模型回答 不可控、不可审计、成本波动大 等问题。

（价值与范围）
从业务侧看，我们希望员工和客服能用自然语言 一站式 完成：查政策、查工单历史、走标准流程，必要时再转人工。
从技术侧看，平台核心包括：Agent 编排（多模式智能切换）、ReAct 等多步推理、多路 RAG 检索、记忆与会话状态、工具系统与 MCP 集成、模型路由与熔断降级、文档 ETL 流水线，以及 全链路追踪与可观测。整体上，我们追求 效果、成本、延迟、可运维 四者的平衡，而不是单纯「接一个大模型 API」。

（你的职责 — 必改）
我在项目里主要负责【例如：Agent 编排与工具运行时 / 多路 RAG 与重排 / 模型网关与降级】，与【前端、运维、算法】同事协作，工作覆盖从【方案设计、接口契约、灰度上线】到【线上指标与排障】。

（代表性结果 — 必改）
上线后，在【例如：近一个季度 / 灰度两个月】内，我们观测到【例如：复杂问题一次解决率提升、P95 延迟下降、单会话 Token 成本可控、转人工率变化】。同时通过 Trace 和指标体系，把典型线上问题从【例如：小时级定位】缩短到【分钟级】的量级。

（收尾）
以上就是我对项目的整体介绍。如果您对某一块技术或业务指标感兴趣，我可以结合 STAR 方法详细展开。

时长提示： 语速正常约 450～550 字/分钟，本段全文约 500～650 字；若超时，优先压缩「技术侧列举」，保留「痛点 + 你的职责 + 一个结果」。

3. 核心模块 STAR 话术（每个模块一份完整话术）

使用说明： 每段均为完整口述稿。请把【】换成你的真实数据；没有的数据删掉或改成「观测到上升趋势」，不要编无法自圆其说的精确数。

3.1 Agent 编排系统

S：
企业需要一个能处理复杂问题的 AI 助手，但 单一 Agent 模式 无法应对所有场景：有的问题只要简单检索即可，有的需要多步推理，有的必须调用内部工具甚至走审批。如果全部用「重模式」，会 又慢又贵；如果全部用「轻模式」，复杂问题 解不掉。

T：
我负责 设计并实现 Agent 编排系统，支持 多种 Agent 模式（如简单问答、ReAct、Plan-and-Execute 等）的 智能切换与组合，并在 延迟与成本预算 内稳定运行，同时保证会话 可追踪、可回放。

A：
我设计了一个 两层编排架构：
第一层是 路由与意图层：结合轻量分类器或规则，以及可选的小模型，把请求分到不同「策略通道」，并给出本轮的 工具权限与最大步数 预算。
第二层是 执行编排层：把一次对话拆成可观测的「步骤」，每步包含：思考、工具选择、工具执行、结果合并。
工程上我重点做了四件事：统一状态机，避免 if-else 散落；并发与超时，工具调用全链路带 deadline；可插拔，新模式以插件注册；观测，每步生成 trace span，便于复盘「为什么选这个模式」。迭代中遇到过 路由误判，后来通过 线上采样评估与阈值调参 改善。

R：
系统能够 自动选择更合适的 Agent 模式，我们观测到 复杂问题解决率提升约 30%（以业务侧「一次解决」或标注集为准），同时平均 步数与 Token 消耗 更可控；排障时借助 trace，「卡在哪一步」的定位时间明显缩短。

3.2 ReAct Agent

S：
很多业务问题不是「一次检索就能回答」，需要 多轮思考 + 多次工具调用，但又要避免模型胡编。ReAct（Reasoning + Acting）适合 可解释、可插工具 的路径；落地常见问题包括：工具选择不稳、步骤过多、死循环风险。

T：
我负责实现 ReAct Agent 的完整执行闭环：在既定工具集合与权限下，让模型按「思考—行动—观察」循环运行，并保证 可停止、可降级、可审计。

A：
我定义了严格的 停止条件：达到最大步数、拿到符合 schema 的最终答案、或触发熔断。每一步把 工具 schema 结构化提供给模型，减少误选。
对工具调用做 幂等与超时；对 observation 做 摘要压缩，避免上下文爆炸。针对 循环，增加 重复检测（同工具同参数、连续相同 observation），以及 人工兜底或策略切换 开关。用典型工单 离线回放，对比步数、成功率、工具错误率。

R：
真实流量采样评估里，工具误用率下降，平均步数下降，线上 因循环导致的超时 明显减少；客服侧反馈复杂场景处理更稳定。

3.3 多路 RAG 检索引擎

S：
企业知识来源多样：制度 PDF、内部 Wiki、工单、结构化表。单一向量检索容易出现 召回不全或召回到错误片段，用户体感是「答非所问」或「引用不对」。

T：
我负责建设 多路 RAG 检索引擎：融合 关键词、向量、结构化查询 等多路召回，并做 重排与引用约束，让生成阶段 有据可查、可定位到 chunk。

A：
检索拆成 召回—融合—重排—上下文组装 四段。召回侧 多路并行；融合侧用 RRF 或加权融合；重排侧用 交叉编码器或轻量模型（视资源而定）。
工程关键点：chunk 策略（标题、表格、代码块区分）、元数据过滤（租户、权限、时间）、引用对齐（答案绑定 chunk id）。建立 badcase 集，对不准样本归因到切分、embedding、权限或重排，再分别优化。

R：
引用正确率 与 首轮解决率 提升；通过监控 空召回率、TopK 分数、重排耗时，调参过程 数据化，而不是凭感觉。

3.4 记忆系统

S：
对话助手若完全没有记忆，用户要重复说上下文；若把大量历史全塞进 prompt，又会 Token 暴涨、噪声干扰、隐私风险 上升。

T：
我负责设计 记忆系统：在 可控成本 下保存对后续决策有用的信息，支持 会话级/用户级 策略，并满足审计与合规。

A：
记忆分为 短期工作记忆 与 长期摘要记忆：短期放本轮关键事实与工具结果摘要；长期用周期性摘要加 结构化槽位（偏好、工单号等）。
写入采用 触发式总结（步数阈值、话题切换），而非每轮都总结。安全上：敏感字段脱敏、租户隔离、可配置 保留周期。检索式注入：先检索记忆再注入，减少噪声。

R：
多轮对话 重复提问率下降，平均 上下文长度更稳定；运维可按策略调整记忆配置而少改业务代码。

3.5 工具系统与 MCP

S：
Agent 要落地必须连接企业内部系统：工单、知识库、CRM、审批等。工具越多，越容易出现 权限难控、接口不一致、调试困难。

T：
我负责建设 工具系统，并引入 MCP（Model Context Protocol） 等标准化接入方式，使工具 可发现、可授权、可观测 地接入编排层。

A：
抽象工具三要素：schema、执行器、审计日志。每个工具声明输入输出、权限域、超时与幂等策略。
对 MCP：客户端连接管理、工具列表同步、调用隔离，每次调用映射到 trace。对旧系统用 适配层 统一成同一工具接口。安全：最小权限，写操作默认需二次确认或走审批链。

R：
工具接入周期从 周级 缩短到 天级；线上问题可快速区分 工具失败还是模型误判；工具调用成功率提升，人工回退减少。

3.6 模型路由与熔断降级

S：
大模型调用存在 超时、抖动、供应商差异；若核心链路没有路由与熔断，容易出现 雪崩，一次抖动拖慢全局。

T：
我负责 模型路由与熔断降级：在预算内选择合适模型，异常时 快速失败或降级 到轻量模型、模板化回答等，保证核心路径可用。

A：
路由策略：按租户、任务类型、敏感度、成本选择模型与参数；配置 并发与队列。
熔断：以错误率、延迟为信号，触发后半开探测；降级 包括缩小上下文、换小模型、只检索不生成、返回固定指引等，均可配置。策略侧有 观测面板：降级原因、次数、影响租户。

R：
尖峰时段 P99 更可控，可用性 提升；简单任务走小模型，单位会话成本 下降。

3.7 文档 ETL 流水线

S：
RAG 效果上限很大程度上取决于 文档入库质量：格式混乱、扫描件、表格跨页、权限变更，都会导致检索与引用失败。

T：
我负责搭建 文档 ETL 流水线：从多源同步、清洗解析、切分、向量化到索引构建，形成 可回放、可重跑 的数据链路。

A：
流水线：采集（增量/全量）→ 解析（PDF/HTML/表）→ 清洗 → chunk → embedding → 索引更新。
失败重试与死信队列，避免单文件阻塞全量；解析失败进入人工复核队列。索引更新采用 双缓冲或蓝绿 思路，减少读到半成品。质量监控：解析成功率、chunk 分布、空文本率。

R：
知识更新从 T+N 天 缩短到 小时级（按实际改）；因「文档过期/未入库」导致的 badcase 占比下降；研发可快速重跑评估。

3.8 全链路追踪

S：
Agent 链路长：路由、检索、工具、模型多次调用。没有 tracing，线上问题只能靠猜，排障成本极高。

T：
我负责落地 全链路追踪：把一次用户请求映射为完整 trace，关联日志与指标，支撑 性能优化与事故复盘。

A：
trace id 在网关、编排、检索、工具、模型网关间传递；关键步骤建 span，记录耗时、输入输出摘要（脱敏）、错误码。trace 与 会话 id、租户 id 关联，支持按租户抽样。流式输出记录 首 token 时间、总时长、截断原因。

R：
平均定位时间从 小时级 降到 分钟级（按实际改）；并推动多轮针对性优化（如某工具超时策略、某检索路径）。

4. 技术难点 STAR 话术（5 个完整故事）

每个故事都按 STAR 完整准备；面试时可根据时长压缩 A，但 不要省略 R。

4.1 模型调用超时和不稳定

S：
上线初期，高峰时经常出现 回答卡住或耗时飙升。监控显示模型侧延迟抖动大，内部链路还存在 重试放大 问题。

T：
目标是在 不牺牲核心体验 的前提下，让系统对抖动 有韧性：用户侧可感知为「稳定可完成」，并避免重试雪崩。

A：
先用 trace 区分 慢在模型首 token、工具、检索还是网关排队。发现主要矛盾是 缺少统一 deadline 与 重试过激。
措施：（1）全链路传递 timeout，模型调用设 首 token 预算 + 总预算；（2）重试仅对 幂等且安全 的环节，指数退避 + 上限；（3）流式输出 让用户先看到进度；（4）长尾请求走 降级路径。持续看 P95/P99、超时率、重试次数。

R：
超时失败率显著下降，P99 更平滑；客服侧「卡住」投诉减少。复盘：早期 观测不足、预算意识弱，后来把 timeout 当成一等公民。

4.2 RAG 检索结果不准确的优化

S：
用户反馈「引用条款不对」或「答案对但依据不对」。问题分散在 chunk、embedding、召回、重排、生成 多环节。

T：
把优化从「凭感觉调参」变成 可度量迭代：建立评测集与线上采样，优先解决 最高频 badcase 类型。

A：
与业务定义 正确性标准（引用必须来自哪类文档、表格字段是否必答）。构建 离线评测集（脱敏），分类统计：空召回、召回不相关、重排错、生成胡编。
针对性优化 chunk、元数据过滤、重排、生成侧 无依据则拒答/追问。每轮改动用 同一套评测集 对比。

R：
引用正确率与满意度提升；迭代可对照指标解释收益，避免「改了 A 坏了 B」却不知道。

4.3 Agent 死循环的排查与解决

S：
部分会话出现 重复思考、重复调用同一工具、步数飙高，最终超时；浪费资源、体验差。

T：
工程上要 检测并终止 不良循环，同时不误杀「多步必要」的复杂任务。

A：
循环分三类：工具返回无效、模型策略漂移、状态未更新导致重复。
落地：重复动作检测（同工具同参数、连续相同 observation）；工具返回 结构化错误码；编排层 步数预算 与 强制切换策略（如改走摘要模式）；trace 标记循环类型。离线回放复现，确认不是简单调小步数能根治。

R：
线上因循环导致的失败与超时明显下降；复杂任务仍可跑足够步数，误杀率可接受。

4.4 Token 成本失控的治理

S：
早期倾向 大上下文 + 强模型，成本快速上升；许多简单问题不需要这种配置。

T：
建立 成本治理机制：让「效果—成本」可权衡、可按租户/场景运营，而不是不可控上涨。

A：
（1）分层路由：简单意图走轻链路，复杂再走重链路；（2）上下文压缩：检索截断与重排、工具结果摘要、记忆摘要策略；（3）预算与告警：单会话 token 上限、租户配额、异常突增告警。用数据看 哪些场景 ROI 高，避免一刀切。

R：
单会话平均成本下降，核心业务指标无明显回退；运营可按租户分级配置，「账单惊吓」风险降低。

4.5 高并发下的性能瓶颈

S：
推广后并发上升，出现 队列堆积、CPU 飙高、检索延迟变大、流式卡顿。

T：
在 不牺牲正确性 前提下做性能治理：找到瓶颈，优先解决 放大效应最大 的环节。

A：
压测 + profiling + trace：压测看吞吐上限，profiling 看热点，trace 看长尾。手段：检索并发控制、连接池、缓存热点、embedding 批处理、水平扩容。引入 背压：网关限流、排队、必要时 优先级（按实际）。先排除 N+1 查询、锁竞争 再单纯加机器。

R：
容量提升后高峰 P95 改善，错误率下降；建立容量基线，大促可提前扩容与演练。

5. 行为面试 STAR 话术

每题一篇完整稿；正式面试可缩到 1.5～2 分钟，但结构保持 STAR。

5.1 「你在项目中遇到的最大挑战是什么？」

S：
项目中期推广加快，业务期望上升，线上出现 成本、延迟、效果 三者拉扯：加能力往往意味着更重链路。

T：
在 资源有限 情况下保证核心场景稳定，让优化 可解释、可复盘，而不是到处救火。

A：
推动 指标体系（效果/成本/延迟）、badcase 复盘、灰度发布。技术上优先解决放大效应大的问题：路由分层、超时预算、检索与工具热点。协作上 用数据周同步，让业务理解「在可控成本内加能力」。

R：
稳定性提升，关键指标改善；团队从「感觉优化」转向 数据驱动。我个人收获是在复杂系统里做 权衡与沟通。

5.2 「你是如何做技术选型的？」

S：
项目涉及编排框架、向量库、网关、观测栈等，早期选错迁移成本很高。

T：
在候选方案里做 可落地对比，输出团队能执行的结论，而不是只堆对比表。

A：
维度：团队熟悉度、社区与风险、性能与成本、运维复杂度、扩展性。每个选项写清 适用边界与不适用场景。向量库看规模、过滤、延迟、运维；观测看现有基础设施。小 POC 用真实链路样本压关键路径。

R：
选型能支撑 半年到一年 演进；关键约束上迁移成本可控。

5.3 「你和团队成员有没有技术分歧？怎么解决的？」

S：
引入更复杂 Agent 模式时，有同事认为应 尽快上更强模型，我认为应先 把路由、预算、观测 做好，否则成本与稳定性会失控。

T：
把分歧变成 可验证决策，而不是立场之争。

A：
用同一批评测样本加 小流量灰度 对比：强模型直出 vs 分层路由 + 中等模型。指标含准确率、P95 延迟、单会话成本。数据证明多数企业场景下 分层路由 ROI 更高，强模型留给少数复杂通道。

R：
方案落地更稳，团队对「为什么这样做」达成共识。我学到 用事实对齐 比争论概念有效。

5.4 「项目中你最自豪的贡献是什么？」

S：
项目从 demo 走向生产时，最大风险不是「能不能跑」，而是 出了问题能不能快速定位与恢复。

T：
希望交付的不只是一个模块，而是 可运营 的能力。

A：
主导或深度参与 全链路追踪、关键指标面板、降级策略 落地，把「黑盒对话」变成可观测系统。推动 trace id 规范 与 可配置熔断降级。带动 线上问题复盘 习惯。

R：
排障效率显著提升，重大故障风险下降。我更自豪的是团队开始用 同一套数据语言 沟通。

5.5 「如果重新做这个项目，你会有什么改进？」

S：
第一次做企业级 Agent 平台，许多决策在信息不完整下做出，这很正常。

T：
若重来，会在 早期 前置几件事，减少后期返工。

A：
更早建立 评测体系与黄金集；更早定义 多租户隔离与安全模型；更早把 成本预算 当一等需求。协作上更早固定 API/工具 schema 契约与版本管理，减少联调损耗。

R：
不改变总体方向，但能降低中后期风险。系统演进必然迭代，关键是 技术债可控、可还。

6. 面试禁忌和注意事项

6.1 不要只说技术，要说业务价值

面试官问项目，本质在问：你为公司带来了什么。技术细节是证据，不是目的。
每段 STAR 的 R 尽量落到：效率、成本、风险、体验 之一。例如：「排障从小时到分钟」是风险与效率；「转人工率下降」是体验与成本。

练习法： 每讲完一个技术点，自问一句：「所以用户或业务感受到了什么？」 答不出就补一句再练。

6.2 不要背书式回答

背书特征：语速均匀、不容打断、追问仍复述同一段。
改进：记 STAR 结构 + 3～5 个关键词，用口语串联。被追问时先 确认层级：架构 / 实现 / 指标 / 取舍。

6.3 要有自己的思考

加分回答通常包含：权衡（为什么）、取舍（放弃了什么）、复盘（如果重来）。结论普通没关系，逻辑自洽 比「标准答案腔」更可信。

6.4 如何应对不会的问题

原则： 诚实、结构化、展示学习能力，不要胡编。

话术模板：

「这块我目前实践经验还不多。我了解的概念是……（1～2 句）。如果让我现在去解决，我会先……（调研/POC/对标开源）。我在【相关经验】里用过类似方法是……」

如果完全没听过：

「这个名词我还没在实际项目里碰过。我能先根据问题描述谈谈我的思路吗？或者您给我一点提示，我沿着您的方向回答。」

6.5 其他注意事项（清单）

  • 贡献表述真实：区分「我主导 / 我负责 / 我参与 / 我配合」。
  • 准备 2～3 个追问点：如为什么 RRF、熔断阈值依据、评测集构造、灰度比例。
  • 控制时长：3 分钟介绍练到不超时；单模块 STAR 练到 2～3 分钟。
  • 准备反向提问：1～2 个有质量的问题（团队稳定性机制、评测文化、线上 on-call）。
  • 肢体语言与节奏：适当停顿，观察面试官是否想插话；不要全程低头背稿。

本指南面向准备投递 AI Agent / LLM 应用 / RAG / 智能客服 等相关岗位的求职者，尤其适合你第一次写技术简历或第一次把 Agent 项目写进简历。文中模板、句式与模块描述均可直接复制，再替换为你的真实数据、公司脱敏名与技术名词。

使用方式建议：

  1. 先通读「总原则」与「常见简历问题诊断」，建立标准。
  2. 按你的主语言（Python / Java / Go）复制「项目经历模板」，填数字与职责。
  3. 从「各模块描述示例」里挑选与你项目相符的句子，拼进「核心职责 / 技术亮点」。
  4. 对照「技能清单写法」整理一页纸技能区，最后做一遍「三问自检」（见文末）。

1. 简历撰写总原则

1.1 STAR 法则在简历中的应用

STAR 是面试常用的表达框架：

字母 英文 含义
S Situation 情境：业务背景、用户是谁、数据/流量规模
T Task 任务：要达成的目标、要解决的矛盾（延迟、成本、准确率等）
A Action 行动：你具体做了什么技术决策与实现
R Result 结果：可验证的指标、上线效果、复盘结论

简历与面试的区别：

  • 面试可以按 STAR 慢慢讲「当时团队情况是……」。
  • 简历篇幅极短，通常把 STAR 压缩成 1～3 句话，不出现「STAR」字样，也不写小说式前因后果。

在简历里的推荐压缩方式：

STAR 要素 简历里怎么写 劣质写法
S 半句到一句：场景 + 规模（用户/请求量/文档量） 「做了一个系统」
T 嵌入动词：为降低/为提升/为满足 SLA 「负责开发」
A 关键技术名 + 你的动作（设计/实现/推动/排障） 「使用各种技术」
R 数字或前后对比 「效果很好」「显著提升」

万能句式（可直接套用）：

在 [场景与规模] 下，为 [目标指标]，采用 [方案 A + 关键技术名]，[你本人主导的动作]，最终实现 [量化结果 / 明确对比]。

再给一个「一条 bullet 里塞满 STAR」的范例：

  • 差： 负责 RAG 模块，使用了向量数据库。
  • 好： 在日均 1 万+ 问答请求的内部知识库场景下，为降低幻觉与尾延迟，采用 混合检索（向量 + BM25）+ Cross-Encoder 重排，并落地 Redis 热点缓存 与 批量向量化 配置，将 P95 端到端延迟从 800ms 降至 320ms，人工抽检 回答准确率从 72% 提升至 86%。

多写几条时的节奏： 第一条偏「整体职责与结果」，后面几条分别写「编排 / RAG / 记忆 / 工具 / 观测」中的深度点，避免每条都是同一种句式开头。

1.2 数字量化的重要性

面试官默认：没有数字 ≈ 没做过、或记不清、或不敢验证。
量化不必全是「百万 QPS」，以下都算有效数字（按你真实能拿到的数据选用）：

类别 可写内容 备注
性能 QPS、RPS、P95/P99 延迟、首字延迟（TTFT）、单次请求成本 压测结果、监控截图可备查
质量 准确率、召回率、F1、MRR、nDCG、用户评分、bad case 占比 离线评测集要写清规模
规模 文档条数、向量维度、索引分片、日活、会话轮次、工具调用次数 体现你处理过真实复杂度
效率与成本 Token 消耗下降 %、GPU 占用、人力节省、迭代周期缩短 Agent 岗很吃香
稳定性 可用性 99.X%、错误率、熔断次数、事故复盘后的改进 偏工程岗必写

若暂时没有线上指标，可以诚实写：

  • 「在自建 200 条 问答集上，F1 从 0.61 → 0.79」；
  • 「压测单机 X req/s 时 P95 Y ms（环境：……）」。

避免虚构业务数据；面试追问时说不清会扣分。

1.3 技术深度 > 广度

广度：一行里写「会 Python、会 LangChain、会 Milvus、会 K8s」——读者无法区分你和「看过教程的人」。

深度：用 2～3 个 bullet 写清「问题 → 你的方案 → 为何不选更简单的做法 → 结果」。

示例对比：

  • 浅： 熟悉 RAG 与 Agent 开发。
  • 深： 针对多跳问答中「检索漂移」问题，对比 仅向量检索 与 HyDE + 混合检索，在业务测试集上选择后者，Recall@5 从 0.58 提升至 0.81，并记录失败样本用于周度迭代。

简历结构建议：

  • 技能清单 / 技术栈一行：体现广度（与 JD 关键词对齐）。
  • 项目经历 bullet：体现深度（每个点尽量有「方案 + 结果」）。

1.4 避免的常见错误

错误类型 说明 改进方向
泛泛动词 「参与」「协助」「熟悉」无下文 改为「设计并实现」「将 X 从 A 优化到 B」「推动上线」
只堆名词 只写技术栈，不写动作 每个技术栈词后面跟「用来解决了什么问题」
抢功 把团队成果全写成「我」 写清「在 X 人团队中负责 Y 子系统」，面试可自洽
无关堆砌 大段传统 CRUD，与 Agent 无关 Agent 岗优先：编排、工具、RAG、评测、成本、延迟、可观测
泄密 写真实客户名、未公开数据 用「某金融客户」「Top3 互联网」；数字用区间或同比
口语与emoji 「很厉害」「🔥」 全文书面语，专业、克制
过长段落 HR 10 秒扫一份简历 多用短句、分号列表；核心数字加粗（若投递系统支持）

2. 技术栈展示

原则： 按 「语言/运行时 → Web 框架 → Agent/模型 → 检索与数据 → 消息与任务 → 可观测与部署」 分组，每组一行或一行半；不要把 30 个词无结构地堆成一行。

三个「不要」：

  1. 不要写「精通」除非你真能经得住深挖。
  2. 不要写已废弃或自己只复制过 Demo 的版本号（如乱写 Python 2.7）。
  3. JD 里强调的词，往前放、写全拼（如对方写 LangGraph，你就别只写 LC）。

4. 各模块的简历描述示例

以下句子可按需拆分、合并、改数字。建议每个模块选 1～2 条 写进简历，避免堆砌。

4.1 Agent 编排模块怎么写

能力点关键词： 状态机、LangGraph、ReAct、规划、人机协同、防死循环、检查点。

可直接使用的描述（多选）：

  1. 基于 LangGraph / 自研有向图 将业务拆成「意图识别 → 规划 → 工具调用 → 反思 → 最终回复」多节点流程，状态持久化至 Redis/DB，支持断点续跑与人工接管。
  2. 配置 最大步数、最大工具调用次数、重复调用检测，将异常会话占比从 X% 降至 Y%。
  3. 实现 并行工具调用 的结果合并与冲突消解，平均完成任务步数减少 X 步，任务完成率提升 X%。
  4. 对 敏感操作（下单、改库）设计 确认节点与二次校验，满足业务风控要求。
  5. 将 Prompt 版本与编排版本 绑定发布，支持灰度与快速回滚，缩短故障恢复时间至 X 分钟内。

4.2 RAG 检索模块怎么写

能力点关键词： 解析、分块、Embedding、混合检索、重排、增量索引、评测。

可直接使用的描述：

  1. 搭建 解析 → 清洗 → 分块 → 向量化 → 索引 全链路，支持 PDF/Word/HTML/表格 等格式，全量索引 X 万篇、增量更新延迟 < X 分钟。
  2. 采用 稠密向量检索 + BM25（Elasticsearch）混合召回，并用 Cross-Encoder / 轻量重排模型 精排，Recall@5 从 X 提升至 Y（Z 条 标注集）。
  3. 针对 短问句、指代、多跳问题 引入 查询改写 / HyDE / 子查询分解，「检索为空」类 bad case 下降 X%。
  4. 建立 文档质量过滤（重复、空页、乱码）与 切块策略实验（固定长度 / 语义分块），离线指标与线上一致性每月对齐。
  5. 对 权限与多租户 做 collection/namespace 隔离，检索仅返回用户可见文档块。

4.3 记忆系统怎么写

能力点关键词： 短期记忆、长期记忆、摘要、滑动窗口、TTL、合规。

可直接使用的描述：

  1. 设计 会话级短期记忆（Redis）+ 用户级长期偏好（PostgreSQL） 分层存储，关键字段满足审计与追溯。
  2. 在上下文长度限制下，采用 摘要压缩 + 滑动窗口 策略，平均 每轮 token 消耗降低 X%，多轮主题连贯性经人工抽检达标。
  3. 对 PII 做脱敏与 可删除设计（用户行使被遗忘权时可清理），满足合规要求。
  4. 实现 记忆召回策略（仅最近 K 轮 / 语义检索历史摘要），避免无关历史干扰当前回答。

4.4 工具系统怎么写

能力点关键词： JSON Schema、OpenAPI、权限、限流、超时、幂等、降级。

可直接使用的描述：

  1. 基于 OpenAPI / JSON Schema 统一工具描述与入参校验，对接 内部 HTTP API、只读 SQL、检索服务。
  2. 为工具调用增加 鉴权、租户隔离、超时、重试与幂等键，失败时 自动降级为纯模型回答或固定话术，工具成功率从 X% 提升至 Y%。
  3. 搭建 工具调用全量日志与请求回放，支撑 bad case 复现与提示词迭代。
  4. 对 高风险工具 采用「模型建议 + 后端二次规则校验」双保险，拦截 X% 越权请求。

4.5 模型路由与容错怎么写

能力点关键词： 多供应商、主备、熔断、429、退避、缓存、成本。

可直接使用的描述：

  1. 实现 主备模型与多供应商路由，按 成本 / 延迟 / 能力 配置策略，故障时 自动切换，核心链路可用性 X%。
  2. 对 429、5xx、超时 实施 指数退避 + 熔断 + 舱壁隔离，并结合 热点问答缓存 削减峰值依赖。
  3. 流式场景处理 客户端断开、中途取消，减少无效计费与僵尸连接数 X%。
  4. 建立 按租户与按模型的成本仪表盘，推动 小模型兜底 + 大模型精修 策略，月度成本下降 X%。

4.6 ETL 流水线怎么写

能力点关键词： Airflow、队列、批处理、embedding 成本、数据质量。

可直接使用的描述：

  1. 使用 Airflow / Dagster / 自研 Cron + 队列 调度文档拉取、清洗、向量化，支持 失败重试、死信队列与告警。
  2. 对 大文件分片与批量 embedding 调用，将 单位文档处理成本降低 X%，全量重建时间从 X 小时 降至 Y 小时。
  3. 建立 数据质量规则（最小长度、编码检测、重复块过滤），脏数据进入索引前拦截率 X%。
  4. 与业务方约定 增量与全量 触发条件，版本化索引 可回滚。

4.7 全链路追踪怎么写

能力点关键词： OpenTelemetry、Trace、Span、LangSmith、SLO、告警。

可直接使用的描述：

  1. 接入 OpenTelemetry，为请求生成 Trace ID，贯通 网关、Agent、检索、工具、模型调用。
  2. 在 LangSmith / Langfuse / 自研看板 上关联单次对话与评测集条目，bad case 定位时间从 X 分钟 缩短至 Y 分钟。
  3. 定义核心 SLI（P95 延迟、错误率、工具失败率） 与 SLO，接入告警与值班流程。
  4. 对 高价值客户 开启 采样策略与日志脱敏 平衡，兼顾可观测与合规。

5. 技能清单写法

目标： 让 HR 与面试官在 10 秒内 判断「是否匹配 JD」，并给你 面试追问入口。

推荐结构（复制后改词）：

text
编程语言：Python（主力）、SQL、Shell
Agent 与 LLM：LangChain、LangGraph、提示词工程、工具调用（OpenAPI/JSON Schema）、简单评测与 bad case 分析
检索与 RAG：Milvus、Elasticsearch、混合检索、重排序、Embedding 模型选型与切块实验
后端：FastAPI、异步 IO、REST/SSE、鉴权与多租户（按实写）
数据：PostgreSQL、Redis、缓存与一致性经验（按实写）
工程化：Docker、CI/CD、单元测试/集成测试、基础 K8s
其他：英语读写（CET-6）、技术博客/开源（如有）

排序技巧：

  1. JD 出现的关键词往前放（岗位写「LangGraph」就显眼写 LangGraph）。
  2. 每一行 2～5 个具体词 即可，不要一行 20 个。
  3. 少用「熟悉/了解」；若用，必须跟具体事实：「了解 LoRA，曾用 X 数据集跑通过一次微调实验」。
  4. 不要单列「ChatGPT」；可写「大模型 API 集成与流式对话」。
  5. 证书与语言：外企或海外团队可写 CET/雅思/托福；与岗无关可省略。

6. 常见简历问题诊断

每个问题都给出 修改前 / 修改后 对比。请将示例中的数字替换为你自己的真实或诚实标注过的数据。

问题 1：描述太笼统

修改前 修改后
负责公司 AI 项目开发。 负责企业知识库问答子系统：基于 FastAPI + Milvus 实现混合检索与重排，覆盖 X 个业务线、Y 万份文档，日均 Z 万次查询。
参与 RAG 优化。 针对检索漂移引入 查询改写与 HyDE，在 500 条业务标注集上 Recall@5 从 0.61 提升至 0.79。
做了 Agent 相关功能。 使用 LangGraph 落地「规划-工具-反思」编排，配置步数上限与重复检测，异常会话占比从 8% 降至 2%。

问题 2：没有量化数据

修改前 修改后
显著降低了延迟。 将检索链路 P95 延迟从 650ms 降至 280ms（含 Redis 缓存与批量向量优化）。
提升了用户满意度。 人工抽检满意度从 3.2/5 提升至 4.1/5；工单转人工率下降 18%。
优化了成本。 通过 小模型意图分类 + 大模型生成，平均每会话 token 消耗下降 35%（基于 X 条日志采样）。

问题 3：技术栈罗列

修改前 修改后
使用 Python、LangChain、向量数据库、Redis。 使用 Python + LangChain 搭建 Agent；向量检索采用 Milvus HNSW 索引，Redis 缓存热点 query 的检索结果，命中后延迟 < 50ms。
熟悉各种大模型。 对接 Azure OpenAI 与自建 vLLM，经统一网关做 流式转发、按租户限流与主备切换。
会 Docker、K8s、Prometheus。 将服务容器化并通过 Helm 部署至 K8s，Prometheus + Grafana 监控 P95 延迟与错误率，告警接入企业微信。

问题 4：项目描述像说明文档

修改前 修改后
本系统是一个基于大模型的智能问答系统，用户在前台输入问题，系统调用后端，后端检索知识库并返回答案。 面向一线客服场景，打通 多轮对话与工单检索；本人负责 检索与重排，通过 混合检索 + Cross-Encoder 将 Top-1 准确率从 52% 提升至 71%，P95 延迟满足 SLA 400ms。
系统采用微服务架构，模块很多，扩展性好。 检索与向量索引独立部署，支持 独立扩缩容；本人负责检索服务 SLO（P95 < 300ms），大促期间通过 只读副本 + 缓存 扛住 3 倍流量。

7. 针对不同背景的简历建议

7.1 应届生 / 小白

侧重点： 学习能力、完整闭环、诚实、可验证（代码/数据集/实验记录）。

  • 项目数量： 1～2 个深挖远好于 5 个浅尝；每个项目能讲清「数据从哪来、指标怎么算、失败怎么改」。
  • 深度来源： 课设、毕设、开源贡献、天池/Kaggle、个人 GitHub；写明 复现了哪篇/哪个仓库，你的增量是什么。
  • 没有线上数据： 明确写「自建 N 条评测集」「离线 F1 / Recall@k」「本地/云主机压测」，不要装成大规模生产。
  • 可写进简历的诚实表述：
text
应届，在校期间完成基于 LangChain 的 RAG 问答项目：实现文档解析、Milvus 索引与混合检索；
在自建 200 条问答集上 F1 达 0.78，代码与实验记录已开源于 GitHub（可附链接）。
  • 避免： 空泛「热爱 AI」、罗列十几门网课、虚构大厂实习。

7.2 1～3 年经验

侧重点： ownership、线上结果、协作边界、技术权衡。

  • 每条经历写清：你负责的模块、与谁协作（前端/算法/运维）、上线后的指标。
  • 主动写 1 条 与 事故、评测、成本、延迟 相关的内容，区分度会明显提高。
  • 权衡示例：「在延迟敏感场景放弃重型重排模型，改用轻量双塔 + 规则后处理，P95 达标且 Recall@5 仅降 2 个点，业务接受。」

摘要句模板：

text
2 年后端经验，近 1 年聚焦 LLM 应用：独立负责检索与评测闭环，推动混合检索与重排上线，
核心业务场景 Top-3 命中率提升 15%，P95 延迟下降 40%。

7.3 转行人员

侧重点： 可迁移能力、学习路径、项目与目标岗的重叠度。

  • 过去工作翻译成新语境： 后端 → 稳定性、性能、接口契约；数据 → ETL、质量、评测集；产品/运营 → 需求拆解、指标体系。
  • 简历上写清投入： 例如「6 个月系统学习 + 2 个完整项目」，减少「只培训过」印象。
  • 传统行业项目可压缩为一行背景，篇幅留给 Agent/RAG/网关 相关经历。

摘要句模板：

text
X 年 Java 后端，系统学习 LLM 应用开发并完成生产级 RAG 项目：
负责 Spring 侧网关与检索编排对接，流式链路 P95 达标；自学 Python 评测脚本与提示词迭代，离线指标与线上一致性按月对齐。

结语 · 投递前三问自检

  1. 这条经历能否在面试里展开讲满 8～10 分钟？（背景、方案、取舍、数据、复盘）
  2. 简历上的数字是否经得起追问？（口径、采样时间、环境）
  3. 关键词是否与目标 JD 对齐？（可适当同义替换，但不要造假经历）

好简历 = 真实经历 + 清晰结构 + 可验证结果。祝你求职顺利。
